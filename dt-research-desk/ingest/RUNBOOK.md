# Weekly ingestion runbook

Rebuilds the **Dual Trend Desk** dashboard from a market-research analyst's Slack output.

Run by **one manual routine, `dt-push`**, which covers both legs against a single watermark pair:

| Leg | Covers |
|---|---|
| ranking | the S&P 1500 ranking report and its `SP1500_DT_Assessment` workbook (posted Mondays) |
| brief | the Weekly Brief — performance pair, cash level, call outcomes (posted Fridays) |

Everything is incremental, so the routine picks up whatever is new whenever it is run, and a long gap
just catches up on the next push.

**Why manual.** Until 2026-10-21 this ran as two cron tasks, `dt-weekly-ingest` (Mon 21:40) and
`dt-friday-brief` (Fri 21:12), sharing one watermark on the theory that whichever fired first would
process whatever was new. On 2026-10-21 both fired in the *same second* — an app-launch catch-up runs
every overdue task at once — and each appended the same nine trades, four calls and two regime entries,
because the pipeline lock covered the build but not the append. More decisively, the step that actually
moves the ranking and performance layers (downloading the PDFs and workbooks) needs a person to approve
desktop control, and that approval **cannot be granted inside an unattended scheduled run at all**. Two
tasks that could never do the one thing only a human could authorise were worse than one routine a
human starts.

## Layout

```
dt-research-desk/
  index.html                 generated — never edit by hand
  ingest/
    state.json               watermarks + processed-file inventory
    data/*.json              curated records (trades, calls, perf, regime, persistence,
                             cash, framework, copy, meta)
                             — all gitignored: they carry licensed third-party content
    data/rankings.json       generated by parse_xlsx.py
    corpus/pdf/  corpus/xlsx/  corpus/pptx/   downloaded sources
    txt/                     generated by extract_pdf.py
    template/                head.html, body.html, app.js
    build-manifest.json      provenance of the last build (owner, payload hash, counts)
    .pipeline.lock           held during an append AND during a build
    lib/                     extract_pdf.py, parse_xlsx.py, build.py, append.py,
                             validate.py, verify_build.py, guard.py,
                             preflight.py, record_publish.py
```

## Sequence

**1. Diff the channels.** Read both since `state.json → channels.*.last_ts`. Channel ids and the
author filter live in `state.json → channels` — this file names no workspace identifiers.
- trade channel — portfolio actions
- publishing channel — research PDFs and ranking workbooks, filtered to the analyst's author id

**2. Append new records to `data/`.** Write the new records to a JSON file keyed by data-file stem and
merge them with the append tool — **never hand-edit the data files**:

```bash
python3 ingest/lib/append.py /tmp/new_records.json --owner dt-push --dry-run   # preview
python3 ingest/lib/append.py /tmp/new_records.json --owner dt-push
```

It takes the same lock `build.py` uses, re-reads each file *inside* the lock so a writer that waited
sees the other's records, and skips any record whose identity key is already present. Re-running the
same Slack window is therefore a no-op, not a duplicate. `persistence` upserts; everything else is
append-if-absent; date-ordered files are re-sorted so an out-of-order insert lands correctly.

One object per new item; keep the existing schema.
- Portfolio action → `trades.json`
  `{date,ticker,name,action:BUY|ADD|TRIM|SELL,direction,size,asset,sector,theme,rationale,source:"slack",url,conviction}`
  Slack permalink: the workspace archive URL for that channel + `/p` + the ts with the dot removed.
- Research report → `calls.json`
  `{date,subject,category,direction,conviction,thesis,evidence,pdf,url,status}`
- Weekly Brief → also append to `perf.json` `{date,dt,spx,cash}` — the "Through Thursday's close" line
  and the cash level. This is the **only** source for the performance series.
- Notable regime shift → `regime.json` `{date,title,dir:bull|bear|neu,body}`
- Cash level stated in a message rather than a brief → `cash.json`
  `{date,cash,note,source:"slack",url}`. The brief-derived levels stay in `perf.json`; a date must not
  appear in both or the ladder double-counts it (validate.py enforces this). The latest disclosed cash
  level is frequently a message, not a brief, so the masthead KPI merges the two.
- A decision rule the analyst states outright → `framework.json`
  `{date,topic,rule,detail,source,url}`. These are *rules*, not dated market views: the trim-vs-sell
  ladder, the dual-bullish screen, the qualitative trend-quality test, the hedging ladder. They are what
  make the trade record legible, and they are easy to miss because they arrive as thread replies to
  someone else's question rather than as `<!channel>` posts.
- Then revisit `persistence.json`: for any prior call on the same subject, set `outcome` to
  Held / Faded / Reversed / Confirmed and update `note`. This table is the point of the exercise —
  it is what makes the dashboard more than an archive.

**3. Download new files.** This DOES run unattended — earlier versions of this runbook said it
could not, which left 29 files queued for six weeks. The Slack app grant persists across sessions, so
`request_access` returns the existing grant with no dialog.

```
request_access(apps=["Slack"])            # returns the stored grant; no prompt
app_list_windows("com.tinyspeck.slackmacgap")
```
If that returns `[]`, Slack is running headless: `open -a Slack`, wait ~6s, list again.

Then, in the window (all coordinates in the 1400x851 frame):

| step | where |
|---|---|
| Files tab | left rail, AX index for "Files" |
| collapse Templates | the `▼ Templates` toggle — doubles the visible rows |
| search box | `(900, 108)` — `app_type` with `overwrite_existing: true`, then Return |
| row 1 download icon | `(1274, 214)` |
| rows 2,3,4,5 | `+132` px each: `346, 478, 610, 742` |

Verify row 1 is the file you want from a screenshot BEFORE clicking — a title search can rank a
different file first. Chain the loop as one batch per file: click row 1's download, type the next
query, press Return; then screenshot to verify the next row 1.

Two things that bite:
- **The download toast grows from the bottom right and covers the lower rows' icons.** When taking
  several files from one result list, click BOTTOM-UP so the toast only ever covers rows you have
  already clicked.
- Search by the most distinctive fragment. Date tokens (`Positioning 20261009`,
  `SP1500_DT_Assessment_2026-09-11`) return exactly one row; title fragments may not.

Files land in `~/Downloads` under their Slack filename. File them to the `dest` in
`state.json → pending_download`, matching the `slack` field — normalise case and punctuation when
comparing, because curly apostrophes and double spaces appear in real titles.

If a file genuinely cannot be fetched, record it in `pending_download` and carry on. That list is a
failure log, not a work queue: anything sitting in it means a run did not finish its job.

**4. Rebuild.** Set `DT_OWNER` so the build is attributable.
```bash
cd dt-research-desk
DT_OWNER=dt-friday-brief python3 ingest/lib/parse_xlsx.py \
  && python3 ingest/lib/extract_pdf.py \
  && DT_OWNER=dt-friday-brief python3 ingest/lib/build.py
```
`build.py` takes the pipeline lock, runs `validate.py` and refuses to build if it errors, writes
`index.html` atomically, runs `verify_build.py` on the output, and stamps `build-manifest.json` with
owner, payload hash and counts. A failure at any gate aborts the build rather than publishing damage.

**5. Preflight, then republish.** Never publish blind — more than one session has written here.
```bash
# WebFetch the artifact first; it saves the page to a local file
python3 ingest/lib/preflight.py <the-file-WebFetch-saved>
```
| exit | meaning | do |
|---|---|---|
| 0 | local differs, live is our own last publish | publish, then `python3 ingest/lib/record_publish.py` |
| 3 | live already matches local | **skip** — nothing changed |
| 2 | **conflict** — live is not what we last published | **do not publish.** Someone else did. Read the live version, fold in anything missing, rebuild, retry |

Publish with `url` from `state.json → artifact_url` so the link is kept, then record it.

**6. Update `state.json`**: both `last_ts`, `last_run`, the processed inventories, `pending_download`.

## Gotchas

- **Report date = data date + 3.** A Monday report carries the prior Friday's workbook. Charts key on
  the *data* date. Don't mix them.
- **Universe size is not fixed.** Row counts drift week to week, and one snapshot jumped by ~45 rows.
  Always express breadth as a percentage of that snapshot's row count, never as a raw count.
- **Duplicate filenames.** Some briefs are posted under an identical filename in different weeks.
  Disambiguate by file size or by the date printed on page 1.
- **The workbook layout drifts; never assume a header position.** Three Sector Summary layouts have
  shipped: header on row 3 at column A; header on row 3 behind two blank columns with the sector split
  into "Sector (Code)" + "Sector Name"; and header on row 4 behind those same blank columns with no
  code column. `parse_xlsx.py` finds the row containing "Rank" and maps "Sector Name" onto "Sector".
  When this broke, six snapshots parsed to ZERO sectors, the build still reported success, and the page
  threw `null.toFixed` on load — killing all five charts. `validate.py` now errors on a snapshot that
  is not 11 named sectors, so the same drift blocks the build instead of shipping blank charts.
- **A green build is not a working page.** The structural check reads the output file; it cannot catch
  a runtime throw. After any data-shape change, open the page and read the console.
- **Browser verification silently stops verifying if the working copy moves.** The preview only
  *executes* scripts for files inside the session's project folder; outside it, it renders a static
  snapshot and `javascript_tool` fails with "No site is open in this tab" — a step written as "open it
  and check the console" then passes vacuously. `verify_build.py` covers the same ground without a
  browser (mount points, data round-trip, external hosts, unrendered template literals, theme tokens)
  and runs automatically at the end of every build. Granting directory access does not fix the preview;
  only moving the copy back inside the project folder does.
- **Scheduled-task definitions are global, not per-session.** They live in `~/.claude/scheduled-tasks/`
  and any session can rewrite any task's prompt with no conflict marker and no notice. Two sessions
  repointed these tasks at different trees within an hour of each other. Before editing a task, say so;
  after editing one, check it still targets the tree named in `state.json → pipeline_id`.
- **Slack file search returns tree entries as well as blobs.** Filtering only on the path prefix inflates
  every count. Always add `select(.type=="blob")`.
- **You are not the only writer.** A forked session republished this artifact once while the schedule
  was live. The lock, the preflight check and `build-manifest.json` exist because of that. If preflight
  returns CONFLICT, something else is driving the pipeline — find it before publishing.
- **Overdue tasks all fire at once.** Scheduled tasks that come due while the app is closed run on next
  launch — together, in the same second. That is how the two old cron tasks collided on 2026-10-21.
  Staggering cron times does not protect against it; only the lock and idempotent appends do.
- **Before appending, check whether the window is already done.** Read `build-manifest.json` and
  `state.json → last_published`. A build newer than your own read of the data means another run has
  already covered this window: stop and report rather than rebuilding on top of it.
- **Not every substantive post is a `<!channel>` post.** Several of the load-bearing methodology
  messages are thread replies to a subscriber's question, and the three webinar posts carry a market
  summary plus a slide deck. An author-filtered sweep that only looks at broadcast posts misses all of
  them. `framework.json` exists because the first nine weeks of them were missed.
- **Never compare perf dates against the latest trade.** A Friday brief lands on days with no portfolio
  action; an earlier version of `validate.py` rejected exactly that and would have blocked a weekly run.
  Future-date checks compare against the clock.
- **Permalinks must come from the post you are citing.** A research call links into `#mo-publishing`
(the publishing channel), a portfolio action into the trade channel. It is easy to reuse an adjacent
  timestamp and produce a link that resolves to the wrong post — this happened to four calls on the first
  build. Before publishing, assert every `calls[].url` contains the publishing channel id and every
  `trades[].url` the trade channel id, both read from `state.json`. If a post has no verified timestamp,
  set `url` to `null` and rely
  on the `pdf` field; a wrong link is worse than no link.
- **Not every report is posted by the analyst.** At least one report was posted by a colleague, so the
  author filter misses it. When a PDF is referenced in a Weekly Brief but absent from the filtered posts,
  search the channel by filename.
- `index.html` is generated. Edit `template/` or `data/`, never the output.

## Limits

The Slack connector reads messages and file *metadata* but cannot download file *bytes*. Retrieval runs
through the Slack desktop app via computer-use, which requires an approval dialog — and that approval
**cannot be obtained inside a scheduled run at all**. `request_access` returns:

> Computer-use access to "Slack" can't be approved during a scheduled run. To grant it, send a message
> in this conversation, or add the app to the scheduled task's settings.

Retrying returns the same result, and the refusal is sticky for the whole session even if the user
writes into it afterwards. This is the reason `dt-push` is hand-started: a run the user launches
themselves can raise the card, and an approval granted during a run is stored on the task and reused by
later runs. The practical first step is therefore **Run now → grant Slack once**.

Until that happens the pipeline still works, it is simply partial: it does steps 1, 2, 4, 5, 6 and
leaves the files in `pending_download` with exact filenames. The *message-derived* layers (trades,
calls, cash, framework, regime, timeline) refresh; the ranking charts stay at the last downloaded
workbook and the performance pair stays at the last downloaded brief. The run report must say which
layers moved and which did not.
